Authentication Methods, Explained Visually

2026-08-21 · zero_rxpc

A tour of how systems actually verify "who are you?" — from the ancient password-in-a-cookie approach to modern passkeys. Covers the mechanics, the tradeoffs, and when each method is the right call.

1. The Landscape

Session-based (Cookies)

Server creates a session on login, stores it server-side, and hands the browser an opaque session ID cookie. Every request round-trips that cookie back to check against server state.

Token-based (JWT)

Server issues a signed, self-contained token after login. No server-side session store needed — the token itself proves identity until it expires.

OAuth 2.0 / OIDC

Delegated auth: "Login with Google/GitHub." A third-party identity provider vouches for the user, and your app never sees their password.

API Keys

A static secret string sent with every request (header or query param), typically for machine-to-machine or third-party integrations, not human logins.

Multi-Factor Auth (MFA/2FA)

Something you know (password) + something you have (OTP app/SMS) or something you are (biometric) — stacked factors to survive a single leaked credential.

Passkeys / WebAuthn

Public-key cryptography bound to a device. No shared secret ever crosses the wire — phishing-resistant by design.

2. Session-Based Auth (Cookies)

Browser: submit login→Server: verify + create session→Server: store session in DB/Redis

Server: Set-Cookie: session_id=xyz→Browser stores cookie→Every request sends cookie back

The classic web pattern. The cookie itself is meaningless (a random ID) — all the actual identity data lives server-side, keyed by that ID. This is why sessions can be instantly revoked (just delete the server-side record) and why it's been the default for decades.

✅ Pros❌ Cons
Instant revocation — delete the session, user is logged out everywhereRequires server-side storage (Redis/DB) — doesn't scale horizontally for free
Small footprint on the wire (just an opaque ID)Needs sticky sessions or a shared session store across server instances
Battle-tested, well-understood security model (HttpOnly, Secure, SameSite flags)Cross-domain/cross-app auth (e.g. mobile app + web app) is awkward

3. Token-Based Auth (JWT)

Browser: submit login→Server: verify + sign JWT→Return JWT to client

Client stores JWT (localStorage/memory)→Send as Authorization: Bearer <token>→Server verifies signature, no DB lookup

A JWT is three base64 chunks — header.payload.signature — where the payload holds claims like {"sub": "user123", "exp": 1755999999}. The server checks the signature (using a secret or public key) instead of looking anything up. This makes JWTs stateless and horizontally scalable, but revocation is the classic pain point: once issued, a JWT is valid until it expires — there's no built-in "kill switch."

// Decoded JWT payload example
{
  "sub": "user_42",
  "role": "admin",
  "iat": 1755990000,
  "exp": 1755993600
}
✅ Pros❌ Cons
Stateless — no server-side session store, scales horizontally with easeHard to revoke early (need a blocklist or short expiry + refresh tokens)
Works cleanly across services/microservices (self-contained claims)Payload is base64, not encrypted — never put secrets in the claims
Good fit for mobile apps and APIs without cookiesToken size grows with claims — bigger than a session cookie

4. OAuth 2.0 / OpenID Connect (Delegated Auth)

Your App→ redirect →Google Login→ user approves →Google → Auth Code

Your App exchanges code→Google returns Access Token + ID Token→Your App verifies ID Token, logs user in

Important distinction: OAuth 2.0 is an authorization framework (grants access to resources/APIs), not an authentication protocol by itself. OpenID Connect (OIDC) is a thin identity layer built on top of OAuth 2.0 that adds the ID Token (a JWT describing who the user is) — that's the piece that actually gives you login/authentication.

This is the "Login with Google/GitHub/Apple" pattern. Your app never touches the user's Google password — it just receives a signed assertion of identity, plus optionally scoped access to their data (calendar, email, etc.) via the access token.

✅ Pros❌ Cons
Users don't create/remember a new password for your appYou depend on a third party's uptime and policies
Offloads MFA, breach detection, password hygiene to the IdPMore moving parts — redirect flows, token exchange, PKCE for public clients
Lower friction signup (one click vs form fill)Account recovery gets tangled if the user loses access to the IdP account

5. API Keys

A long, random static string issued once, then sent with every request — usually in an Authorization: Bearer <key> or a custom header like X-API-Key. Built for machine-to-machine calls (a backend calling Stripe, a script hitting your own API), not for human login flows — there's no "session," no expiry by default, and no built-in concept of a logged-in user identity beyond "whoever holds this string."

✅ Pros❌ Cons
Dead simple to implement and useNo expiry by default — a leaked key works forever until manually revoked
Great for service-to-service and third-party integrationsNo standard for scoping/rotation — every provider does it differently
No login flow/redirect neededPoor fit for human users — no MFA, no session semantics

6. Multi-Factor Authentication (MFA / 2FA)

Factor 1: Password (something you know)+Factor 2: OTP app / SMS / security key (something you have)+Factor 3: Biometric (something you are)

MFA doesn't replace a login method — it stacks on top of one. Even if a password leaks in a breach, the attacker still needs the second factor. TOTP apps (Google Authenticator, Authy) generate a 6-digit code from a shared secret + current time, refreshed every 30 seconds. SMS-based 2FA is the weakest common option (vulnerable to SIM-swapping) but still far better than password-only.

✅ Pros❌ Cons
Massively reduces account takeover risk from leaked/reused passwordsAdds friction to every login — some users disable it if not enforced
TOTP/hardware keys work offline, no network dependencySMS-based OTP is vulnerable to SIM-swap attacks
Cheap to add on top of existing password authLost device/recovery flow needs careful design (backup codes etc.)

7. Passkeys / WebAuthn (Passwordless)

Register: device generates key pair→Public key sent to server→Private key stays on device (secure enclave)

Login: server sends challenge→Device signs with private key→Server verifies with stored public key

Built on the WebAuthn standard, passkeys use asymmetric cryptography instead of a shared secret. There is no password to phish, leak, or reuse across sites — the private key never leaves the device (it's locked behind Face ID, Touch ID, or a PIN). This is why passkeys are considered phishing-resistant: even a perfect fake login page can't extract a private key that never gets transmitted anywhere.

✅ Pros❌ Cons
Phishing-resistant by construction — nothing secret ever crosses the wireCross-device/platform support still maturing (sync via iCloud Keychain, Google Password Manager, etc.)
No password to remember, leak, or reuseRecovery story is newer — losing all your devices is a real edge case to design for
Faster login UX than password + OTPNot yet universally supported by every login page/legacy system

8. Which One Should You Actually Use?

✅ Session cookies: classic server-rendered web apps, single backend, need instant revocation (banking, admin panels).

✅ JWT: microservices, mobile APIs, anything that needs to scale stateless auth checks across many servers without a shared session store.

✅ OAuth/OIDC: consumer apps where lowering signup friction matters, or when you need scoped access to a third-party's data (Google Calendar, GitHub repos) on the user's behalf.

✅ API keys: server-to-server integrations, internal tooling, public APIs for developers.

✅ MFA: layer it on top of literally everything with real account value — it's not a replacement, it's a multiplier.

✅ Passkeys: new products today, or migrating high-value accounts away from password-only — this is where the industry is heading (see: Apple, Google, Microsoft all pushing passkeys hard since 2023).
