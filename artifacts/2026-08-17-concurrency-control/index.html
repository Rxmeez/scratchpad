Concurrency Control, Explained Visually

2026-08-17 · zero_rxpc

How databases let many transactions run at once without corrupting data or blocking each other into the ground. Covers pessimistic locking, optimistic concurrency, and MVCC — with timelines, tradeoffs, and a quiz at the end.

1. The Core Problem

Concurrency control exists because multiple transactions touching the same rows at the same time can produce wrong results if left unmanaged. Classic failure modes:

  • Lost update — Tx A and Tx B both read a value, both write back based on the stale read; one write silently overwrites the other.
  • Dirty read — Tx B reads a value Tx A wrote but hasn't committed yet; Tx A rolls back, and Tx B acted on data that never really existed.
  • Non-repeatable read — Tx A reads a row twice in the same transaction and gets two different values because Tx B committed a change in between.
  • Phantom read — Tx A re-runs the same query and a new row appears because Tx B inserted a matching row in between.

Key insight: the strategy you pick trades off between correctness guarantees, throughput under contention, and how gracefully conflicts are handled. There is no free lunch.

3. Pessimistic Locking

Assume conflicts will happen, so lock the row before touching it. Other transactions wanting the same row must wait.

Tx A: BEGIN
Tx A: SELECT * FROM accounts WHERE id=1 FOR UPDATE  → row locked
Tx B: BEGIN
Tx B: SELECT * FROM accounts WHERE id=1 FOR UPDATE  → BLOCKS, waits
Tx A: UPDATE accounts SET balance = balance - 100 WHERE id=1
Tx A: COMMIT  → lock released
Tx B: (unblocked) reads the fresh balance, proceeds

Example (Postgres/MySQL): SELECT ... FOR UPDATE takes a row-level exclusive lock until the transaction ends.

✅ Pros❌ Cons
Simple to reason about — no retry logic neededContention causes waiting → throughput drops under load
Guarantees no lost updates, everRisk of deadlocks if lock order isn't consistent
Good fit for high-conflict workloads (e.g. inventory decrement)Long-held locks block unrelated readers/writers

4. Optimistic Concurrency Control (OCC)

Assume conflicts are rare. Don't lock anything — read freely, then at write time check whether the data changed since you read it. If it did, reject and retry.

Tx A: SELECT balance, version FROM accounts WHERE id=1  → balance=500, version=7
Tx B: SELECT balance, version FROM accounts WHERE id=1  → balance=500, version=7
Tx A: UPDATE accounts SET balance=400, version=8 WHERE id=1 AND version=7  → 1 row affected, OK
Tx B: UPDATE accounts SET balance=600, version=8 WHERE id=1 AND version=7  → 0 rows affected — version moved on, retry!

Example (application-level, works on any SQL DB): add a version or updated_at column, include it in the WHERE clause of every update, check the affected row count.

✅ Pros❌ Cons
No locks, no blocking — great read/write throughputWasted work on conflict — the losing transaction must retry
No deadlock riskBad fit for high-contention hot rows (constant retries)
Scales well for low-conflict, read-heavy workloadsRequires app-level discipline (every writer must check version)

5. MVCC (Multi-Version Concurrency Control)

Used by Postgres, MySQL/InnoDB, Oracle. Instead of locking rows for reads, the database keeps multiple versions of each row and gives every transaction a consistent snapshot as of when it started. Readers never block writers, and writers never block readers.

Row v1 (balance=500)Tx A updates →Row v2 (balance=400)

Tx B, started before the update, still sees v1 via its snapshot. Old versions get vacuumed/purged once no transaction needs them.

Example (Postgres): every row has hidden xmin/xmax system columns marking which transaction created/deleted that version. SELECT just filters versions visible to your transaction's snapshot — no lock needed.

✅ Pros❌ Cons
Readers never block writers, writers never block readersStill need locks/version checks for write-write conflicts
Great for read-heavy + moderate write workloadsOld row versions pile up — needs vacuum/GC (Postgres bloat is a real ops concern)
Default behavior in Postgres/MySQL — you get it for freeLong-running transactions can block vacuum, growing table bloat

6. Which One Should You Use?

✅ Pessimistic locking when: conflicts are frequent and correctness must be guaranteed immediately (e.g. seat booking, inventory decrement, bank transfers on the same account).

✅ OCC when: conflicts are rare, workload is mostly reads with occasional writes, and you can cheaply retry on conflict (e.g. editing a user profile, CMS documents).

✅ MVCC (usually automatic): you're on Postgres/MySQL and want good read/write concurrency by default — you get this without doing anything, but should still add app-level version checks for write-write safety on hot rows.

❌ Avoid: mixing pessimistic locks across many tables without a strict, consistent lock ordering (deadlock magnet). Avoid pure OCC on very hot rows with many concurrent writers (thrashing retries).
