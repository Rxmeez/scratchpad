Rate Limiting Algorithms, Explained Visually

2026-08-18 · zero_rxpc

Five common rate limiting algorithms, how each one actually behaves under bursts, where each shines, and where each falls apart — with visual timelines, pros/cons, and a quiz at the end.

1. Why Rate Limiting Exists

Rate limiting caps how many requests a client (user, API key, IP) can make in a given time period. It protects backend resources from overload, enforces fair usage across tenants, prevents abuse (scraping, brute force, DDoS), and keeps costs predictable for pay-per-request downstream services.

Key insight: the algorithm you pick controls the shape of allowed traffic — smooth and steady vs bursty, strict vs forgiving — and that shape has real consequences for both your infra and your users' experience.

2. The Five Algorithms at a Glance

Fixed Window→Sliding Window Log→Sliding Window Counter→Token Bucket→Leaky Bucket

3. Fixed Window Counter

Divide time into fixed chunks (e.g. every 60s), count requests per chunk, reset to 0 at the boundary. Limit = 5 requests/window.

Window 1 [0-60s]Window 2 [60-120s]
reqreqreqreqreqreq  |  reqreq

Problem: 5 requests land at 0:59, then 5 more at 1:01 — 10 requests in 2 seconds, both windows individually "compliant."

Example: Redis INCR key with EXPIRE 60 on first increment; reject once counter exceeds the limit.

✅ Pros❌ Cons
Dead simple to implement — one counter, one TTLBoundary burst problem — up to 2x limit can slip through at window edges
Very cheap (O(1) memory per client)Not smooth — allows sudden bursts right after reset

4. Sliding Window Log

Store a timestamp for every request in a sorted set. On each new request, drop timestamps older than the window, then count what's left.

Log: [12:00:01, 12:00:15, 12:00:40, 12:00:58]

New request at 12:01:05 → drop timestamps before 12:00:05 → log becomes [12:00:15, 12:00:40, 12:00:58, 12:01:05] → count=4

Example: Redis sorted set (ZADD + ZREMRANGEBYSCORE to prune + ZCARD to count) per client key.

✅ Pros❌ Cons
Perfectly accurate — no boundary burst issue at allMemory grows with request volume (stores every timestamp)
True rolling window, smooth enforcementMore expensive per-request (sorted set ops) — costly at high QPS

5. Sliding Window Counter (Hybrid)

A cheaper approximation of the sliding log: keep fixed-window counters, but weight the previous window's count by how much it overlaps the current sliding view.

estimated_count = current_window_count + previous_window_count × overlap_fraction

e.g. 30% into the current window → weight previous window at 70%: 3 + (5 × 0.7) = 6.5 → round and compare to limit

Example: Cloudflare and many API gateways use this — two Redis counters (current + previous fixed window) instead of a full log.

✅ Pros❌ Cons
Near sliding-log accuracy at fixed-window memory costApproximation — assumes uniform request distribution within the window
O(1) memory per client, cheap to computeSlightly more complex to implement correctly than fixed window

6. Token Bucket

A bucket holds up to N tokens, refilled at a steady rate. Each request consumes one token; if the bucket is empty, the request is rejected (or queued). Crucially, unused tokens accumulate — this is what allows controlled bursts.

Bucket capacity: 5 tokens, refill rate: 1 token/sec

Example: AWS API Gateway, Stripe's API, and most cloud rate limiters use this by default. Implemented via current_tokens = min(capacity, current_tokens + elapsed_time × refill_rate) on each request.

✅ Pros❌ Cons
Allows legitimate short bursts (good UX for spiky-but-normal traffic)Bursts can still momentarily overload downstream if capacity is large
Smooth average rate over time, industry-standard choiceSlightly trickier to reason about than fixed window (two parameters: capacity + refill rate)
Cheap — O(1) state per client (token count + last refill time)-

7. Leaky Bucket

Requests enter a FIFO queue (the "bucket") and are processed ("leak out") at a fixed, constant rate — regardless of how bursty the input is. If the queue is full, new requests are dropped.

Bursty input: 10 requests arrive instantly

Queue holds up to 5→ processed at 1 req/sec, steady drip out →Downstream sees perfectly smooth 1 req/sec

Requests 6-10 dropped — queue was full

Example: network traffic shaping, and API gateways that need to protect a downstream system with a strict fixed processing rate (e.g. a legacy system that can't handle bursts at all).

✅ Pros❌ Cons
Perfectly smooths output rate — best protection for fragile downstreamsNo burst tolerance at all — legitimate spiky traffic gets queued/dropped
Predictable, constant outbound rateAdded latency — requests wait in queue even when server has spare capacity

9. Which One Should You Use?

✅ Token bucket when: you're rate-limiting a public API and want to allow short legitimate bursts (most common real-world choice — Stripe, GitHub, AWS all use variants of this).

✅ Sliding window counter when: you want near-perfect accuracy without the memory cost of a full log — good default for high-traffic gateways (Cloudflare's approach).

✅ Leaky bucket when: protecting a fragile downstream that truly cannot handle any burst (legacy systems, hardware-constrained services, strict SLA queues).

✅ Fixed window when: you need something simple fast and can tolerate some boundary imprecision (internal tools, low-stakes limits).

❌ Avoid: sliding window log at very high QPS per client (memory/CPU cost balloons) — and avoid fixed window for anything security-sensitive (brute-force protection, login attempts) since the boundary burst can be exploited.
