Log-Based CDC, Explained Visually

2026-08-17 · zero_rxpc

Companion deep-dive to a CDC interview quiz question. Learn how log-based Change Data Capture actually works, how to set it up end-to-end, and when it's the right (or wrong) tool for the job.

1. The Core Idea

Every transactional database already keeps an internal write-ahead log (WAL) — a durability mechanism used to survive crashes. Log-based CDC tools read this log after the fact, asynchronously, and turn each row-level change into an event.

Key insight: you're not querying the table. You're tailing a log the database was writing anyway. That's why it's cheap on the source — no extra SELECT load, no polling.

2. Architecture

Postgres / MySQL— WAL / binlog →Debezium Connector— events →Kafka Topic

Kafka then fans out to:

Data Warehouse   Search Index   Cache Invalidation   Downstream Services

3. Setup Walkthrough (Postgres + Debezium + Kafka)

Step 1 — Enable logical replication in postgresql.conf:

wal_level = logical
max_replication_slots = 4
max_wal_senders = 4

Step 2 — Create a publication for the tables you want to track:

CREATE PUBLICATION my_cdc_pub FOR TABLE orders, customers;

Step 3 — Deploy Kafka Connect + Debezium connector, then register it:

curl -X POST localhost:8083/connectors -H "Content-Type: application/json" -d '{
  "name": "orders-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "prod-db.internal",
    "database.dbname": "shop",
    "table.include.list": "public.orders,public.customers",
    "plugin.name": "pgoutput",
    "topic.prefix": "cdc"
  }
}'

Step 4 — Consume the events. Each Kafka message looks like:

{
  "before": { "id": 42, "status": "pending" },
  "after":  { "id": 42, "status": "shipped" },
  "op": "u",
  "ts_ms": 1755432000000
}

op tells you the operation: c=create, u=update, d=delete, r=initial snapshot read.

Step 5 — Load into your warehouse via a sink connector (Snowflake, BigQuery, Redshift) or a stream processor (Flink / ksqlDB) if transformation is needed first.

4. Pros vs Cons

✅ Pros❌ Cons
Near real-time (sub-second to seconds)Requires Kafka + Connect infra (ops overhead)
Minimal load on source DB (log tailing, not querying)WAL retention must be tuned — connector downtime can bloat WAL
Captures deletes and full history, in orderSchema changes need careful handling (schema evolution)
Decouples producers from consumers via KafkaInitial snapshot of large tables can be slow / heavy
Works across many DBs (Postgres, MySQL, MongoDB, SQL Server)Overkill for small or low-change datasets, or batch-tolerant use cases

5. When Is It Suitable?

✅ Use log-based CDC when: you need near real-time sync, source DB load must stay minimal, you need reliable delete capture, or multiple downstream systems need the same change stream (fan-out via Kafka).

❌ Avoid / overkill when: nightly batch is good enough, dataset is small, you don't already run (or want to run) Kafka infrastructure, or the team lacks ops capacity to maintain connectors and monitor replication lag.
